# dispatch: 단일 루프 우선, agent는 비용 값을 할 때만
기본은 메인 세션이 skill로 단독 작업한다. agent는 도구이며 작업당 0~3개만, 습관적으로 셋 모두 쓰지 않는다. 표에 없는 작업은 agent 없이 하고 성공 기준·검증자·중단 조건을 먼저 정한다.

## 1. 작업 유형별 구조
| 작업 | agent (수) | 사람 승인 | 이유 |
| --- | --- | --- | --- |
| 작은 코드 수정 | 없음 (0) | 커밋 전 | 맥락 유지 |
| 기존 코드 수정 | 저장소 첫 진입에만 explorer (0~1) | 커밋 전 | 분석이 곧 수정에 쓰임 |
| 복잡한 기능 | 테스트 통과 후 reviewer (1) | 설계 직후, 커밋 전 | 독립 점검 |
| 원인 후보가 여럿인 버그 | explorer 병렬 (2~3) | 커밋 전 | 넓게 탐색, 비용 증가 |
| 대규모 리팩터링 | 독립 모듈만 병렬(§3), 모듈당 1 | 커밋 전 | 그 외는 메인에서 순차 |
| 기술 스택 비교, 문헌·선행기술 조사 | 축마다 explorer 병렬 (2~3) | 없음 | 독립 조사 |
| 보고서 / 논문 / 특허 | evidence-verifier (1) | 개요, 최종본 | 숫자는 출처와 일치 |
| PPT | 슬라이드 숫자는 evidence-verifier (1) | 구성안, 최종본 | 스토리라인·취향은 메인 |
| 아키텍처 / ADR | 승인 전 reviewer 1회 선택 (0~1) | 설계 직후 | 결정은 사람 |
| UI/UX | 없음 (0) | 화면마다 | 취향은 사용자와 반복 조율 |

기능 구현은 해당 skill이 있으면 requirements-analysis(모호할 때) → system-architect(새 의존성·스키마·공개 API·아키텍처, 설계 대화와 승인) → code-change 순으로 한다.

## 2. 호출 규칙
- 위임 전 확인: 내 다음 단계에 의존하지 않고 실행 가능한가, 결과를 출력만 보고 판단 가능한가, 넓은 조사인가. 하나도 아니면 직접 한다. 순차 작업을 역할로 쪼개기, 한두 파일 수정, 자기 결과 확인용 호출은 하지 않는다.
- 기본은 포그라운드. 병렬·백그라운드는 시간·철저함의 이득이 분명할 때만, 토큰이 늘어남을 사용자에게 알린다.
- agent는 대화를 물려받지 않는다. 지시문에 필요한 맥락(제약 포함)을 모두 담고 한 번에 한 단계만 맡긴다. 양식: `단계 / 목표 한 줄(결과가 분명한 일에만 필수) / 읽을 것 / 쓸 것(출력 파일 이름) / 하지 말 것`
- 출력 계약: 결론(1~3줄), 근거, 이슈(최대 5개, 중요도순), Uncertainty, Next action. 필요할 때만 추가 질문하고 과정 로그는 요구하지 않는다.
- reviewer에게는 요청(목표 한 줄·성공 기준), 변경 파일과 diff, 검사 명령과 결과, 의존하는 테스트·검증 데이터 경로(타당성 판정용)를 넘기고 대화 기록·추론·자기 평가는 넘기지 않는다. 읽기 전용이며, 메인이 지적마다 재현·확인해 맞는 것만 고치고 기각은 사유와 함께 보고한다. 건수는 `eval_log.csv`의 `reviewer_defects`, `rejected_findings`에 적는다.

## 3. 병렬 작업
기본은 조사만 병렬. 독립 모듈 구현은 모두 충족할 때만 병렬로 한다.
1. 인터페이스가 확정되어 문서로 적혀 있다.
2. 작업자 사이에 공유되는 변경 가능 상태·파일이 없다.
3. 작업자마다 git worktree 또는 브랜치가 있다.
4. 각 결과를 단독으로 검증할 수 있다(테스트 명령의 종료 코드).
5. 메인이 병합 후 전체 검사를 다시 돌리고, reviewer는 병합 결과만 판단한다.

무거운 빌드·테스트는 동시에 2개 이하.

## 4. 모델·노력 수준
등급 기준이며 사용 가능한 모델에 맞춘다(비용과 이름은 바뀜). 메인 모델은 사용자가 정한다.
- 분류, 짧은 요약, 파일 목록: 저비용(haiku급), 낮음
- 탐색, 근거 수집: 저비용~중간, 낮음~중간
- 일반 구현, 문서 초안: 중간(sonnet급), 중간
- 복잡한 설계, 어려운 추론, 보안 검토: 고성능, 높음
- 최종 검증: 검증 대상의 난이도에 맞춤, 중간~높음

모델·노력 수준·모드는 작업 경계(/clear)에서만 바꾼다. 중간에 바꾸면 프롬프트 캐시가 무효화될 수 있다.

## 5. hook과 skill
- hook(결정적): 포맷·린트·테스트 실행, 위험 명령 차단·경로 제한, 압축 후 메모리 재주입.
- skill(판단): 코딩 방식·리뷰 절차, 문제 해결 전략, 프로젝트 지식·문서 구조.

## 6. 외부 skill
`third_party/README.md`의 검토 관문을 통과해 승인된 것만 쓴다. 기본은 꺼짐. 승인하면 아래 표에 사용 조건을 한 줄로 적고, 표에 없으면 쓰지 않는다.
| skill | 켜는 프리셋 | 사용 조건 | 승인일 |
| --- | --- | --- | --- |
| interview-me | 프리셋 무관(`init_project.py --ext interview-me`로 설치한 프로젝트) | 새 기능·문서·화면 착수 때 질문 5개 이하, 한 번에 하나. 버그 수정·작은 수정·유지보수·비대화 실행 제외. 결과는 `docs/intent/`가 아니라 INTENT(`.ai/INTENT.md` 또는 `.ai/intent/`)에 저장 | 2026-11-25 |

## 7. 중단 조건 기본값
skill에 값이 없으면 이것을 따른다(위임 재시도 포함). 같은 단계가 2번 연속 실패하거나 같은 문제로 3번 되돌리면 멈추고 근거, 시도한 것, 막힌 곳을 보고한다.

## 8. 승인 기록
승인받은 산출물(명세, 설계 노트, 개요, 스토리라인, 구성안)은 `.claude/hooks/approval_hash.py`가 있으면 `record <파일>`로 해시를 남기고, 이후 작업 전에 `check <파일>`이 0이어야 한다. 승인 후 파일이 바뀌면 재승인한다. hook이 없으면 `UNVERIFIED: approval`.

## 9. BLOCKED
근거·권한·입력이 부족하면 지어내지 말고 `.ai/BLOCKED.md`에 `막힌 것 / 시도한 것 / 필요한 것`을 적고 멈춰 보고한다(Uncertainty에 합친다). 읽기 전용 agent는 결론 첫 줄에 `BLOCKED: <사유>`를 쓰고 메인이 기록한다.
