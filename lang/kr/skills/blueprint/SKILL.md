# blueprint

## 루프 계약
- 성공 기준: 설계서의 모든 칸(기능, 화면, 데이터, 보안 3줄)이 채워졌거나 `[TODO]`로 남아 질문 목록에 있고, 사용자가 승인했다. 설계서에 없는 기능·화면·표는 코드에 없다.
- 검증자: 사용자 승인(사람 관문). 그 뒤 `system-architect`가 있으면 데이터·보안·스택을 그 설계 대화로 검토한다. 선택적으로 `reviewer`가 구현이 설계서와 일치하는지 점검한다.
- 중단 조건: 같은 칸에 질문을 2번 해도 답이 없거나 승인 없이 설계서 수정이 3회 이어지면 멈추고 남은 칸과 선택지를 요약해 사용자에게 묻는다. 막히면 dispatch.md의 BLOCKED 규칙.

## 절차
1. 먼저 읽는다: `.ai/INTENT.md`, `CLAUDE.md`, 저장소(README, 패키지·설정 파일), 기존 `.ai/BLUEPRINT.md`. 이미 답이 있는 칸은 묻지 않고 무엇을 확인했는지 말한다.
2. `.ai/BLUEPRINT.md`가 있으면 새로 만들지 않는다. 비어 있거나 `[TODO]`인 칸만 질문한다. 추가 지시사항이 변경 요청이면 코드 말고 설계서부터 고치고 5절에 한 줄을 더한 뒤, 바뀐 부분만 읽고 그 부분만 코드에 반영한다.
3. 질문은 한 번에 하나만 한다. 답이 설계를 바꿀 때만 묻고, 아니면 기본값을 이유와 함께 제안한다. 이미 정한 것은 다시 묻지 않는다. 초반에는 누가 쓰는지, 무엇을 하려는지, 이번에 안 만들 것을 예시 답 없이 열린 질문으로 묻는다. 내가 고른 것은 사용자 합의와 구분해 "내 판단"으로 표시한다. 질문, 설명, 요약은 처음부터 끝까지 한국어로 쓰고 중간에 영어로 바꾸지 않는다("질문 3" 같은 머리말도 한국어).
4. 아래 양식으로 쓴다. 한 줄 소개와 프로젝트 목표는 `.ai/INTENT.md`가 원본이다(여기에는 링크만). `.ai/INTENT.md`가 비어 있으면 같은 답으로 초안을 제안만 하고 승인 뒤 기록한다.
5. 다 채우면 사용자 승인을 받는다(상태: 요구 정리 승인, 이때 dispatch.md의 승인 기록 규칙대로 해시를 남긴다). 승인 전에는 코드, 스캐폴딩, 의존성 설치, 프로젝트 생성을 하지 않는다(읽기·탐색은 가능). 승인 뒤 `system-architect`가 있으면 그 설계 대화로 데이터·보안·스택을 검토하고, 문제가 있으면 사용자에게 보고하고 다시 질문·제안한 뒤 설계서를 고친다.
6. 최종 결정이 나면 상태를 `최종`으로 바꾸고 dispatch.md의 승인 기록 규칙대로 해시를 다시 남긴다(`approval_hash.py`가 없으면 `UNVERIFIED: approval`). 이후 바뀌면 재승인한다. 구현은 `code-change`로 최종 승인 뒤 시작한다.
7. 새 파일이므로 `python .ai/kb.py new asset .ai/BLUEPRINT.md`로 등록하고, 카드 본문의 `무엇`(앱 이름, 사용자, 화면·기능 수 한 줄)과 `언제 보나`(구현·변경·리뷰 전)를 채운다. 설계서가 바뀌면 카드 요약과 `updated`도 고친다.

## 양식 (60줄 안팎, 한 줄에 사실 하나)
```

상태: 초안 | 요구 정리 승인 | 최종
목표·범위: .ai/INTENT.md 참고

## 1. 기능: 누가 무엇을 할 수 있나
- (사용자 1):
- (사용자 2, 예: 관리자):
이번에는 만들지 않을 것:
-

## 2. 화면: 어떤 화면이, 어떤 순서로
1. (화면 이름): 보여야 할 것
공통: (예: 휴대폰 위주, 큰 글자, 모든 문구 한국어)

## 3. 데이터: 앱이 기억해야 할 표
- (표 이름): 칸1, 칸2, 칸3

## 4. 보안: 세 줄
1. 키 보관: API 키는 환경 변수 파일(.env)에만 둔다. 화면 코드와 깃허브에는 올리지 않는다.
2. 로그인 권한: (누가 로그인해야 하는지, 누가 무엇을 볼 수 있는지)
3. 데이터베이스 접근 규칙: (데이터베이스 규칙으로 막을 것. 예: 다른 사람의 정보는 조회할 수 없다)

## 5. 변경 기록
- (날짜) (무엇을 왜 바꿨는지)
```

## 하지 말 것
- 질문하지 않고 모호한 칸을 임의로 채우지 않는다. 모르면 `[TODO]`로 두고 묻는다.
- 설계서에 없는 기능·화면·표를 코드에 넣지 않는다. 필요해 보이면 설계서 변경을 제안한다.
- `.env`나 키 값을 읽거나 설계서에 적지 않는다.
